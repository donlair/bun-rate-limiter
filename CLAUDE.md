## Project Overview

**bun-rate-limiter** is a lightweight, zero-runtime-dependency task scheduler and rate limiter library. Built with Bun, it runs on Node.js 18+, Vercel, AWS Lambda, and other platforms. The key differentiator is composable throttlers that work together (spacing, token buckets, interval caps) with the scheduler enforcing the most restrictive constraint.

## Architecture

### Core Component Hierarchy

```
RateLimiter (Facade)
    ├─ StandardScheduler (Coordinator)
    │   ├─ IQueue (Storage)
    │   │   ├─ PriorityQueue (default)
    │   │   └─ ArrayQueue (FIFO)
    │   ├─ IThrottler[] (Sync rate limiting)
    │   │   ├─ SpacingThrottler
    │   │   ├─ IntervalThrottler
    │   │   └─ TokenBucketThrottler
    │   └─ IAsyncThrottler[] (Distributed rate limiting)
    │       ├─ RedisSpacingThrottler
    │       └─ RedisTokenBucketThrottler
    ├─ Job (Task wrapper)
    └─ EventBus (Event handling)
```

### Key Design Patterns

**Throttler Composition**: Multiple throttlers compose by taking the maximum delay. The scheduler asks each throttler "how long to wait?" and waits for the maximum delay returned. This allows combining strategies like "at least 100ms between requests AND max 2000/minute".

**Sync vs Async Throttlers**:
- **IThrottler** (sync): Local in-memory rate limiting. Methods: `getNextRunDelay()`, `notifyJobStarted()`
- **IAsyncThrottler** (async): Distributed rate limiting via Redis. Methods: `acquire(context)`, returns `{ granted, delayMs, permit? }`

**The `limits` Shorthand**: The `limits` config in `RateLimiterOptions` is syntactic sugar that creates throttlers:
- `{ minDelayMs: 100 }` → creates `SpacingThrottler(100)` or `RedisSpacingThrottler` (if Redis backend)
- `{ tokenBucket: {...} }` → creates `TokenBucketThrottler` or `RedisTokenBucketThrottler`
- `{ interval: {...} }` → creates `IntervalThrottler` (local only, not supported with Redis)

When `backend: { type: 'redis' }` is specified, the same `limits` config automatically creates Redis-backed throttlers instead of local ones.

**StandardScheduler Processing Loop**:
- Without async throttlers: synchronous loop with `setTimeout` for throttling
- With async throttlers: async `processLoop()` that uses `peek()`, `acquire()` permits, then `dequeue()` to prevent race conditions
- Uses generation counter to detect when `clear()` or `resetAsyncThrottlers()` is called

### Source Structure

- `src/index.ts` - Main entry point, exports RateLimiter facade and resolveThrottling logic
- `src/core/` - Core abstractions (Job, EventBus, types, errors, limits builder)
- `src/scheduler/` - StandardScheduler implementation
- `src/strategies/queue/` - Queue implementations (PriorityQueue, ArrayQueue)
- `src/strategies/throttle/` - Throttler implementations
  - `IThrottler.ts` / `IAsyncThrottler.ts` - Interfaces
  - Local: `SpacingThrottler`, `IntervalThrottler`, `TokenBucketThrottler`
  - Redis: `redis/RedisSpacingThrottler`, `redis/RedisTokenBucketThrottler`

### Build Process Specifics

The build creates three outputs:
1. **Type declarations** (`dist/**/*.d.ts` + `.d.ts.map`): Generated by `tsc` with `declaration: true`
2. **ESM bundle** (`dist/index.js`): Built by `bun build` with `--format esm`
3. **CJS bundle** (`dist/index.cjs`): Built by `bun build` with `--format cjs`

**Important**: After TypeScript generates `.d.ts` files, `scripts/rewrite-dts-imports.ts` rewrites imports from `.ts` to `.js` to match Node.js ESM resolution (e.g., `from './foo.ts'` → `from './foo.js'`). This is required for proper type resolution in consuming projects.

### Package Publishing

The `files` field in `package.json` controls what gets published to npm:
```json
"files": ["dist", "LICENSE", "README.md"]
```

The `src/` directory is intentionally excluded to reduce package size. The published package contains only compiled outputs (`dist/`), not TypeScript source.

### Testing Patterns

- Unit tests live in `tests/` mirroring `src/` structure (e.g., `tests/core/Job.test.ts` for `src/core/Job.ts`)
- Integration tests in `tests/integration/` test cross-component behavior
- Redis tests are marked with `.integration.test.ts` suffix and should be skipped if Redis is unavailable
- Use `queue.resetAsyncThrottlers()` between tests to clear distributed rate limiter state

### Code Style

The project uses Biome for linting and formatting:

- 100 character line width
- 2 space indentation
- `noExplicitAny` is a warning (but disabled in test files)

- **`tsconfig.json`**: Main config with strict mode, `noEmit: true` (for IDE/editor)

## Common Development Workflows

### Adding a new throttler strategy
1. Create interface/implementation in `src/strategies/throttle/`
2. Implement either `IThrottler` (sync) or `IAsyncThrottler` (async/Redis)
3. Export from `src/index.ts`
4. Add corresponding tests in `tests/strategies/`
5. Consider adding to `buildThrottlersFromLimits` or `buildAsyncThrottlersFromLimits` in `src/core/limits.ts` if it should be available via `limits` config

### Modifying the scheduler
- Core logic is in `src/scheduler/StandardScheduler.ts`
- The `tryNext()` method is the entry point for starting new jobs
- For async throttlers, the `processLoop()` method handles permit acquisition
- The `generation` counter tracks when `clear()` or `resetAsyncThrottlers()` is called to abandon ongoing work

### Testing distributed features
- Redis integration tests require a running Redis instance
- Use `RedisClient` from Bun (`import { RedisClient } from 'bun'`)
- For Node.js adapters, see `examples/node-ioredis/` and `examples/nextjs-server-action/`

## Important Constraints

- **Zero runtime dependencies**: The library has no dependencies in `package.json`
- **Runs anywhere**: Built with Bun, but compiles to standard JS for Node.js 18+
- **Redis is optional**: Distributed throttlers require Redis, but local throttlers work standalone
- **No automatic retries**: Failed tasks are not automatically retried; users must implement retry logic
- **No Redis fallback**: If Redis becomes unavailable, tasks fail (no automatic fallback to local limiting)
